# 05.04 — Module: Generation

Status: Draft
Last updated: 2026-11-05

Generation turns a valid project into code and documentation that the customer downloads (ADR 0007) or produces
with the open-source CLI. It lives in `packages/core`. P1 covers **dbt for Snowflake** (UC-030) and **Markdown
documentation** (UC-032). Requirement identifiers: `GEN-xxx`.

## 1. General rules
- GEN-001: Only a project without validation errors is generated (VAL-000).
- GEN-002: Output is deterministic: the same project gives byte-identical files (stable ordering, no timestamps).
- GEN-003: Every generated file starts with a comment saying it is generated by Atlas and must not be edited, with
  the project id and the format version.
- GEN-004: Generated names are the ids of the spec, unchanged (target models and columns are already lowercase
  `snake_case`); SQL identifiers of sources keep their case, quoted.

## 2. dbt project (Snowflake)

### 2.1 Layout
```
dbt_project.yml
models/sources/<system>.yml          one dbt source per system (landing database and schema, §3.3 of the metamodel)
models/<domain code>/<model>.sql     one SQL model per target model
models/<domain code>/<model>.yml     descriptions, data types and tests of the model
tests/atlas/<model>__<check>.sql     data tests that dbt has no generic test for (unique combination, fail behaviors)
```
- GEN-012: Business rules and value mappings are **expanded inline** in the SQL, marked `/* rule <id> */` and
  `/* value mapping <id> */`. Macros were considered and rejected: a rule receiving the result of another expression
  would need Jinja nested inside Jinja, which dbt cannot read. Their documentation is in the Markdown output (§3).
- GEN-010: A chained model (MM-111) is read with `{{ ref('<model>') }}`; a source table with
  `{{ source('<system>', '<dataset>') }}`. dbt then orders the models itself.
- GEN-011: The model's `materialization` becomes its dbt `materialized` config (`table`, `view`, `incremental`).

### 2.2 Structure of a model
One common table expression (CTE) per branch, then the union, then the consolidation:

```sql
with
branch_sap_fr as (
    select <one expression per target column> , 'SAP_FR' as source_system
    from <driving dataset> as c
    left join <dataset> as s on <condition>
    left join <looked-up dataset> as lk_1 on <lookup match>        -- one per lookup step
    where <filter>
    qualify row_number() over (partition by <dedup key> order by <dedup order>) = 1   -- deduplicate
),
branch_oracle as ( ... ),
unioned as (
    select * from branch_sap_fr union all select * from branch_oracle
),
consolidated as ( ... )      -- only when `match` is given (§2.3)
select <target columns> from consolidated
```
- GEN-020: `group_by` becomes `group by` in the branch CTE; aggregation steps become aggregate functions.
- GEN-021: A `lookup` becomes a `left join` to the looked-up dataset with an alias of its own; it is many-to-one by
  construction (MM-201). `on_missing: fail` and `map_values` with `on_unmatched: fail` produce no error inside the
  query; they add a **data test listing the offending rows or values** (`tests/atlas/<model>__<branch>__fail_<n>.sql`),
  which is easier to act on than a runtime error.
- GEN-023: Every column is cast to its target type, except a source column or an explicit conversion that already has
  exactly that type.
- GEN-022: Every branch CTE selects the columns in the same order, cast to the target type, so the union is safe.

### 2.3 Consolidation
- GEN-030: Without `match`, the result is the union (`union all` or `union` for `union_distinct`).
- GEN-031: With `match`, rows whose match columns are all filled are grouped by them; the surviving row is the first
  by branch priority (`row_number()`); rows with an empty match value are kept as they are (MM-132).
- GEN-032: Column survivorship uses window functions over the same groups: `first_not_null` →
  `first_value(col ignore nulls)` ordered by its priority; `most_recent` → ordered by its `by` column descending.

### 2.4 Expressions
| Spec | Snowflake |
|---|---|
| column `c.KUNNR` | `c."KUNNR"` |
| literal `{ value: "FR01" }` | `'FR01'`, typed by context (`'2'::number(…)` when compared with a number) |
| `default` | `coalesce(x, v)`; with `also_empty`: `coalesce(nullif(trim(x), ''), v)` |
| `constant` | the literal |
| `convert` `cast`, `on_error: fail` | `cast(x as T)` |
| `convert` `cast`, `on_error: set_null` | `try_cast(x as T)` (text input) |
| `convert` `parse` date | `to_date(x, 'YYYYMMDD')`, or `try_to_date` with `set_null` |
| `map_values` | `case when x is null then null when x = 'a' then 'b' … else <x, default or null> end` |
| `case` | `case when … then … else … end` |
| `concat` | `array_to_string(array_construct_compact(p1, p2, …), sep)` (skips empty parts, §5.2) |
| `rule` | the rule's logic expanded with its arguments, `/* rule <id> */ (…)` |
| `aggregate` | `sum`, `count`, `count(distinct …)`, `min`, `max`, `avg` |
| `sql` | the expression, `{{ current }}` replaced by the pipeline value, aliases unchanged |

- GEN-040: A pipeline is generated by nesting each step around the previous value (`current`).
- GEN-041: Logical types map to Snowflake types: `string(n)` → `varchar(n)`, `integer`/`bigint` → `number(38,0)`,
  `decimal(p,s)` → `number(p,s)`, `float` → `float`, `boolean` → `boolean`, `date` → `date`, `time` → `time`,
  `timestamp` → `timestamp_ntz`, `timestamp_tz` → `timestamp_tz`, `binary` → `binary`, `json` → `variant`.

### 2.5 Function catalog (`calculate`)
| Function | Arguments | Snowflake |
|---|---|---|
| `add`, `subtract`, `multiply`, `divide` | 2 numbers | `a + b`, `a - b`, `a * b`, `a / b` |
| `round` | number, digits | `round(a, d)` |
| `abs` | number | `abs(a)` |
| `nullif` | value, value | `nullif(a, b)` |
| `coalesce` | 2 or more values | `coalesce(…)` |
| `upper`, `lower`, `trim` | text | `upper(a)`, `lower(a)`, `trim(a)` |
| `substring` | text, start, length | `substr(a, s, l)` |
| `left`, `right` | text, length | `left(a, n)`, `right(a, n)` |
| `length` | text | `length(a)` |
| `replace` | text, search, replacement | `replace(a, s, r)` |
| `ltrim_zeros` | text | `ltrim(a, '0')` (SAP numbers with leading zeros) |
| `date_add` | unit, number, date | `dateadd(unit, n, d)` |
| `date_diff` | unit, date, date | `datediff(unit, d1, d2)` |
| `date_trunc` | unit, date | `date_trunc(unit, d)` |
| `year`, `month`, `day` | date | `year(d)`, `month(d)`, `day(d)` |

- GEN-050: The catalog is defined once in `packages/core` (MM-202); each generator translates every function. A
  missing function is added to the catalog, not written as SQL by the generator.

### 2.6 Tests
| Quality check | dbt |
|---|---|
| `not_null`, `unique` | generic tests `not_null`, `unique` |
| `accepted_values` | generic test `accepted_values` (values, or the target values of a value mapping) |
| `relationship` | generic test `relationships` |
| `unique_combination` | a data test in `tests/atlas/` |

- GEN-060: Grain key columns get `not_null` and a uniqueness test automatically (MM-101).
- GEN-061: `severity: warn` becomes dbt `config: {severity: warn}`.

## 3. Markdown documentation
- GEN-070: One page per target model: description, grain, domain, branches (sources, joins, filters), consolidation,
  then one row per column with its definition, type and, for each branch, its provenance in plain words
  ("SAP France: KNA1.LAND1, converted to text(2)").
- GEN-071: One page per business rule (statement, parameters, logic in plain words) and per value mapping (table).
- GEN-072: An index page lists domains and their models, with the share of unstructured logic (VAL-070).

## 4. Not in P1
Other warehouses (UC-031), ODCS export (UC-033, P3), incremental strategies beyond `materialized`.
